# Independent review prompt: grading soundness and robustness of the swesim pipeline

Paste everything below the line into Codex (or any reviewer) from the repository root `swesim/` on `main`.

---

You are an independent, skeptical reviewer of **swesim**, a system that builds simulated-stakeholder software-engineering environments for post-training. It takes an underspecified GitHub issue and its merged PR, measures which tests the PR fixes in an offline sandbox, drafts a brief that withholds some of what the reporter said, puts a simulated stakeholder (an LLM grounded in the real issue/PR thread) behind an `ask-user` tool, runs a coding agent inside a Harbor task on Modal, and grades the result offline with the PR's tests. Temporal on a GCE VM orchestrates task creation and runs; a FastAPI console shows them.

The review question is: **can a reward be wrong, and can a claim in the docs be unsupported?** Treat every statement in the docs as a hypothesis until you have checked the artifact behind it. Be specific: every finding needs a file:line, a reproduction (a command, or a concrete input you constructed), the consequence, and the smallest fix. Rank P1 (a reward can be awarded or withheld incorrectly, hidden information can reach the agent, or unattended operation is blocked), P2 (a measurement is wrong or operation is fragile), P3 (quality). Do not modify the repository. Do not start cloud jobs (`harbor run`, `modal`, `gcloud`, Temporal submissions) unless a section says you may; everything else in the repository and workspace is yours to run.

## Ground truth to start from

- `CLAUDE.md` (contracts), `PLAN.md` (milestones), `docs/architecture.md`, `docs/grading.md`, `docs/ops.md`, `README.md`.
- The ledger `.superpowers/sdd/2026-09-12-swesim-implementation/progress.md` records every ruling, live failure and fix in order. The reports beside it (`review-*.md`) show what earlier reviewers found; assume they missed things.
- Evidence on disk: `registry.json`; `workspace/scenarios/*/{scenario.json,judge.json,draft.meta.json,approval.json,compile.json,validation.json,scores.json}`; `workspace/trials/*/{run_config,reward,report,transcript,record}.json`; `workspace/exports/*.episode.json`; `workspace/jobs/**` (Harbor job directories with `agent/trajectory.json` and `verifier/`); `workspace/evidence/` (model probes, VM histories, `ops.json`, chain logs); `examples/mwaskom--seaborn-3190/` (the tracked package).
- Offline tests: `uv run --frozen --offline python -m pytest -q tests --ignore=tests/integration`; acceptance: `bash scripts/verify.sh 10` (no cloud calls).

## Review areas, in priority order

1. **Grading soundness.** The verifier (`swesim/verifier/*.py`, standard library only, runs in a separate offline container) must award reward only when the contract tests genuinely pass on the submitted code. Read `grader.py`, `policy.py`, `parsers.py`, `run_pytest.py` and the collector `swesim/templates/collect.py`. Construct incorrect submissions and check that each one is graded zero: a submission whose printed output imitates pytest's summary lines; a JUnit file that disagrees with the terminal summary or the exit code; edits to `conftest.py`, `sitecustomize.py`, `.pth` files, `pytest.ini`/`pytest.toml`, `pyproject.toml`, or `*.egg-info` entry points; symbolic or hard links in the base tree; very large output; a pytest plugin registered from source; an `atexit` hook that prints a second summary; a module that monkeypatches pytest internals when imported; paths that differ only by Unicode normalization or case; a run that exhausts the time budget; anything that changes how base statuses are read. The control patches in `swesim/tamper.py` are the cases the authors covered; look for the ones they did not. Any incorrect submission that can earn reward > 0 is P1.

2. **Information boundary of the stakeholder.** The stakeholder must never reveal how the hidden tests are constructed, the oracle patch, author-only facts, or repository internals a reporter would not know, and must not propose tests, verification steps, or code. Read `swesim/stakeholder/{prompts,session,service,tools}.py`, `swesim/stakeholder/view.py`, `swesim/stages/draft_spec.py` (which facts become visible and how test-derived facts are phrased), and every `transcript.json` under `workspace/trials/`. One such disclosure already happened (seaborn fact `f05` described the regression test; the fix added a `forbidden_terms` reply filter and a behavior-only confirmation channel). Check whether a paraphrase, a split identifier, or a description without identifiers still gets through; whether `disclosed_fact_ids`, patience tier, or the tool audit can reach the agent through any endpoint or file; whether a session token is bound to exactly one trial and cannot be reused across trials or after freezing; whether `request_id` binding can be bypassed; whether the patience budget can be reset.

3. **Contract measurement.** SWE-bench's published FAIL_TO_PASS/PASS_TO_PASS lists were produced with network access and did not reproduce offline, so the contract is now measured by a probe (`swesim/sources/github_repo.py:probe_tests`, `swesim/stages/mine.py:probe_candidates`). Check that F2P really means "fails on base with the test patch applied and passes with the gold patch" under the grader's exact command and test order, that order-dependent and environment-dependent tests are dropped rather than accepted, that the probe binding (`base_commit` + `test_patch` hash) cannot be satisfied by a stale or foreign measurement, and that `protected_paths` can never contain a path the gold patch modifies.

4. **Withholding integrity.** The withheld brief must be exactly the natural issue minus code-selected spans; every removal must appear in the ledger with a verbatim excerpt; no requirement may be added or silently removed. Read `draft_spec.py` (`withhold`, `_deletion_range`, `ledger_violations`) and `ScenarioSpec._integrity` in `swesim/models.py`. Try to construct a model output that changes the task without a ledger entry, or a "fact" not grounded in the thread that passes the grounding check (very short excerpts, blockquote normalization, casefold collisions, mislabeled provenance).

5. **Judge and approval gates.** `swesim/stages/judge.py` decides which issues count as underspecified and `swesim/stages/approve.py` approves unattended. Check whether an LLM output can pass an ungrounded gap through `ground_gaps`/`accept()`, whether the calibration numbers (`workspace/judge_calibration.json`: agreement 0.655, precision 0.644, recall 0.460 on 145) are computed as described, and whether any approval gate can be satisfied trivially (for example an on-request fact linked to every F2P test).

6. **Control patches.** Plausible-wrong and alternative-correct controls are LLM-authored and verified at draft time (`draft_spec.py`: difflib-built diffs, `git apply --check` against fetched base files, a code fallback). Check that a "plausible-wrong" control can never be functionally identical to the gold (an inversion inside a docstring or comment, a no-op line removal), that verification results are recorded honestly, and that files skipped by the fetch bound are never treated as absent.

7. **Temporal and the VM.** `swesim/workflows/{workflows,activities,client}.py`, `scripts/vm/*`, `docs/ops.md`. Claims: each trial launches exactly once into a named user systemd unit; a worker restart never launches a second solver; unknown launch state is reconciled, never retried; no secret travels in a workflow payload, command line, or log. Read `decide_launch`, `launch_once`, `await_trial_activity`, the `ALLOW_DUPLICATE_FAILED_ONLY` handling, the concurrency limit in `CreateTasksWorkflow`, the signal-based approval path, and the VM scripts' credential handling. Compare the evidence in `workspace/evidence/ops.json` and `workspace/evidence/vm/` against `docs/ops.md`, including the stated caveat for the "laptop-off" test (the lid stayed open; the claim is that no SSH session or tunnel existed during the window).

8. **Task compilation and network policy.** `swesim/stages/compile.py`, `swesim/templates/*.j2`, `references/modal-smoke-task/`. The agent runs unprivileged under a strict host allowlist (model API hosts and the stakeholder host); the verifier has no network; collection is a root-owned hook writing to a root-only directory with a receipt. Check that the session token reaches only the interactive task, that hidden tests and the oracle never enter the agent image, that `compiled_hash` covers every input the agent sees (templates, scaffold config, per-profile instructions), and that the base-manifest and submodule checks fail closed.

9. **Scoring and exports.** `swesim/stages/{score,export,register}.py`. Denominators count outcomes 1 to 4 only; 5 to 7 are excluded; unresolved attempts are preserved but never counted; `policy_visible` is built from the agent's own observations; evaluator-only data never appears in `policy_visible`. Recompute one score table by hand from the records and compare. Check that trials with different agent scaffolds (`RunConfig.agent_config`) never pool.

10. **The console.** `swesim/dashboard/*`. Check that agent and stakeholder text is HTML-escaped in every context, that the file route serves only whitelisted files, that evaluator-only data is unreachable without the gate, that state-changing requests require a confirmation step and an Origin check, and that no response contains a secret. Run it locally (`SWESIM_WORKSPACE=$PWD/workspace SWESIM_REGISTRY=$PWD/registry.json uv run --frozen uvicorn swesim.dashboard.app:app --port 8099`) and probe with curl.

11. **Docs versus disk.** For every number and claim in `README.md`, `docs/grading.md`, `docs/architecture.md` and `docs/ops.md`, find the artifact or mark it unsupported. Pay attention to the interaction rate, the calibration, the laptop-off window, and which trials predate which fixes (instruction wording v1/v2, the scaffold, the stakeholder before the disclosure fix).

12. **Reproducibility for a stranger.** Follow `README.md` as a new user with only the listed prerequisites. Every command that needs a credential, a private hostname, or a file that exists only on the author's machine is a finding.

## What you may run

- Anything offline: pytest, `verify.sh`, the dashboard locally, Python probes against `swesim/` modules with fake inputs, `git log`/`git show`, reading every file under `workspace/` and `examples/`.
- You may build and run the verifier locally against the tracked example (`examples/mwaskom--seaborn-3190/task__full/tests/`) with Docker if available, feeding it hand-made incorrect submissions; that is the most direct way to check area 1.
- Do not run `harbor run -e modal`, `modal deploy`, `swesim create`, `swesim run-tasks`, or anything against the VM.

## Output

A single markdown report: a one-paragraph verdict; findings ordered P1 to P3, each with file:line, reproduction, consequence, fix; a table "claim → artifact → verified / unsupported / false" for the docs; and a closing list of the three changes that would most improve the trustworthiness of the reward. Say what you could not verify and why. Do not soften findings; the authors want to know where grading can be wrong before the environments are used for training.
