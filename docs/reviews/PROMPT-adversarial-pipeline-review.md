# Adversarial review prompt: the whole swesim pipeline

Paste everything below the line into Codex (or any reviewer) from the repository root `swesim/` on `main`.

---

You are an adversarial reviewer of **swesim**, a system that manufactures simulated-stakeholder software-engineering environments for post-training: it takes an underspecified GitHub issue plus its merged PR, measures which tests the PR fixes in an offline sandbox, drafts a brief that withholds some of what the reporter said, puts a simulated stakeholder (an LLM grounded in the real issue/PR thread) behind an `ask-user` tool, runs a coding agent inside a Harbor task on Modal, and grades the result offline with the PR's tests. Temporal on a GCE VM orchestrates creation and runs; a FastAPI console shows them.

Your job is to break it. Assume everything in the docs is a claim until you have checked the artifact behind it. Be specific: every finding needs a file:line, a reproduction (command or a described input), the consequence, and the smallest fix. Rank P1 (invalidates rewards, leaks, or blocks unattended operation), P2 (wrong measurement or fragile operation), P3 (quality). Do not fix anything. Do not launch cloud jobs (`harbor run`, `modal`, `gcloud`, Temporal submissions) unless a section says you may; everything else in the repository and workspace is yours to run.

## Ground truth to start from

- `CLAUDE.md` (contracts), `PLAN.md` (milestones), `docs/architecture.md`, `docs/grading.md`, `docs/ops.md`, `README.md`.
- The ledger `.superpowers/sdd/2026-09-12-swesim-implementation/progress.md`: every ruling, live failure and fix, in order. The review reports beside it (`review-*.md`) show what earlier reviewers found; assume they missed things.
- Evidence on disk: `registry.json`; `workspace/scenarios/*/{scenario.json,judge.json,draft.meta.json,approval.json,compile.json,validation.json,scores.json}`; `workspace/trials/*/{run_config,reward,report,transcript,record}.json`; `workspace/exports/*.episode.json`; `workspace/jobs/**` (Harbor job dirs with `agent/trajectory.json` and `verifier/`); `workspace/evidence/` (model probes, VM histories, `ops.json`, chain logs); `examples/mwaskom--seaborn-3190/` (the tracked package).
- Offline tests: `uv run --frozen --offline python -m pytest -q tests --ignore=tests/integration`; acceptance: `bash scripts/verify.sh 10` (no cloud calls).

## Attack surfaces, in priority order

1. **Reward hacking by the solver.** The verifier (`swesim/verifier/*.py`, stdlib only, runs inside a separate offline container) must be unbeatable by anything the agent can put in `/testbed` or `/app`. Read `grader.py`, `policy.py`, `parsers.py`, `run_pytest.py` and the collector `swesim/templates/collect.py`. Try to construct a submission that earns reward without passing the real tests: forged `-rA` summary lines, JUnit tampering, `conftest.py`/`sitecustomize`/`.pth`/`pytest.ini`/`pyproject` edits, `*.egg-info` entry points, symlinks or hard links in the base tree, output floods, pytest plugins registered from source, `atexit` hooks printing a fake summary, monkeypatching pytest internals from imported source, editing protected files through a path the normalizer does not cover (unicode, case, `..`), exhausting the time budget so reruns are skipped, or making base statuses look different. The tamper controls (`swesim/tamper.py`) are the ones the authors thought of; find the ones they did not. Every control that could earn reward > 0 is a P1.

2. **Stakeholder leakage.** The stakeholder must never reveal hidden-test construction, the oracle, author-only facts, or repository internals the reporter would not know, and must never propose tests, verification steps or code. Read `swesim/stakeholder/{prompts,session,service,tools}.py`, `swesim/stakeholder/view.py`, `swesim/stages/draft_spec.py` (which facts become visible and how `tests-NNN` facts are phrased), and every `transcript.json` under `workspace/trials/`. One leak already happened (seaborn fact `f05` described the regression test; the fix added a `forbidden_terms` filter): check whether the filter can be evaded (paraphrase, split identifiers, describing the test without its identifiers), whether `disclosed_fact_ids`/`tier`/tool audit can reach the agent through any endpoint, whether a session token can be forged, replayed across trials, or used to unfreeze, whether `request_id` binding can be bypassed, and whether the patience budget can be reset.

3. **Contract measurement.** SWE-bench's published FAIL_TO_PASS/PASS_TO_PASS lists were produced with network access and did not reproduce offline, so the contract is now measured by a probe (`swesim/sources/github_repo.py:probe_tests`, `swesim/stages/mine.py:probe_candidates`). Check that F2P really means "fails on base with the test patch applied and passes with the gold patch" in the grader's exact command and order, that order-dependent and environment-dependent tests are dropped rather than silently accepted, that the probe binding (`base_commit` + `test_patch` hash) cannot be satisfied by a stale or foreign probe, and that `protected_paths` can never contain a path the gold patch modifies.

4. **Withholding integrity.** The withheld brief must be exactly the natural issue minus code-selected spans; every removal must appear in the ledger with a verbatim excerpt; no requirement may be added or silently deleted. Read `draft_spec.py` (`withhold`, `_deletion_range`, `ledger_violations`, `ScenarioSpec._integrity` in `swesim/models.py`). Try to make the model's output change the task without a ledger entry, or make a "fact" that is not grounded in the thread pass the grounding check (short excerpts, blockquote normalization, casefold collisions, provenance mislabeling).

5. **Judge and gates.** `swesim/stages/judge.py` decides which issues are "underspecified" and `swesim/stages/approve.py` auto-approves unattended. Check whether an LLM output can smuggle an ungrounded gap past `ground_gaps`/`accept()`, whether the calibration numbers (`workspace/judge_calibration.json`: agreement 0.655, precision 0.644, recall 0.460 on 145) are computed as described, and whether any auto-approval gate can be satisfied trivially (e.g. an on-request fact auto-linked to every F2P test).

6. **Control patches.** Plausible-wrong and alternative-correct controls are LLM-authored and verified at draft time (`draft_spec.py`: difflib-built diffs, `git apply --check` against fetched base files, code fallback). Check that a "plausible-wrong" control can never be functionally identical to the gold (docstring/comment inversion, no-op line drops), that verification results are recorded honestly, and that unfetched files are never treated as absent.

7. **Temporal and the VM.** `swesim/workflows/{workflows,activities,client}.py`, `scripts/vm/*`, `docs/ops.md`. Claims: each trial launches exactly once into a named user systemd unit; a worker restart never launches a second solver; unknown launch state is reconciled, never retried; no secret travels in a payload, argv, or log. Read `decide_launch`, `launch_once`, `await_trial_activity`, the `ALLOW_DUPLICATE_FAILED_ONLY` handling, the semaphore in `CreateTasksWorkflow`, the signal-based approval path, and the VM scripts' token handling. Check the evidence in `workspace/evidence/ops.json` and `workspace/evidence/vm/` against the claims in `docs/ops.md` (including the "laptop-off" caveat: the lid stayed open; the claim is absence of any SSH session or tunnel during the window).

8. **Task compilation and network policy.** `swesim/stages/compile.py`, `swesim/templates/*.j2`, `references/modal-smoke-task/`. The agent runs unprivileged under a strict allowlist (model API hosts + the stakeholder host); the verifier has no network; collection is a root hook writing to a root-only directory with a receipt. Check that the session token reaches only the interactive task, that the hidden tests and oracle never enter the agent image, that `compiled_hash` binds every input the agent sees (templates, scaffold config, per-profile instructions), and that the base-manifest and submodule guards fail closed.

9. **Scoring and exports.** `swesim/stages/{score,export,register}.py`. Denominators count outcomes 1–4 only; 5–7 excluded; unresolved attempts preserved but never counted; `policy_visible` built from the agent's own observations; evaluator-only data never in `policy_visible`. Recompute a score table by hand from the records and compare. Check that trials with different agent scaffolds (`RunConfig.agent_config`) never pool.

10. **The console.** `swesim/dashboard/*`. XSS through agent or stakeholder text, path traversal in file routes, evaluator-only data reachable without the gate, CSRF posture of the POST endpoints, secrets in any response. Run it locally (`SWESIM_WORKSPACE=$PWD/workspace SWESIM_REGISTRY=$PWD/registry.json uv run --frozen uvicorn swesim.dashboard.app:app --port 8099`) and probe.

11. **Docs versus disk.** For every number and every claim in `README.md`, `docs/grading.md`, `docs/architecture.md`, `docs/ops.md`, find the artifact or mark it unsupported. Pay attention to what is said about the interaction rate, the calibration, the laptop-off window, and which trials predate which fixes (instruction wording v1/v2, scaffold, stakeholder v1 before the leak fix).

12. **Reproducibility for a stranger.** Follow `README.md` as a new user with only the listed prerequisites. Every command that would need a credential, a private hostname, or a file that only exists on the author's machine is a finding.

## What you may run

- Anything offline: pytest, `verify.sh`, the dashboard locally, Python probes against `swesim/` modules with fake inputs, `git log`/`git show`, reading every file under `workspace/` and `examples/`.
- You may build and run the verifier locally against the tracked example (`examples/mwaskom--seaborn-3190/task__full/tests/`) with Docker if available, feeding it hand-made tampered submissions; that is the most direct way to attack item 1.
- Do not run `harbor run -e modal`, `modal deploy`, `swesim create`, `swesim run-tasks`, or anything against the VM.

## Output

A single markdown report: a one-paragraph verdict; findings ordered P1 → P3, each with file:line, reproduction, consequence, fix; a table "claim → artifact → verified / unsupported / false" for the docs; and a closing list of the three changes that would most improve the reward's trustworthiness. Say what you could not verify and why. Do not soften findings; the authors want to know where it breaks before it is used for training.
