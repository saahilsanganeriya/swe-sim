## Findings you could not fix in the plan

Each item distinguishes a design disagreement or unverified runtime claim from an executed failure. The spec remained read-only.

1. **Major — spec §§10.2, 10.4; P Task 3: same-process report forgery remains possible.** Submitted code still executes in pytest and can attack its reporting and imports. Extra files, random report names and reruns are not independent trust boundaries. **Smallest verification:** run an applicable malicious source patch that forges both terminal and JUnit evidence; record the result. The plan fails closed on disagreement but cannot prove agreement means correctness. Strong process-external behavioral grading would require dropping additional experimental scope.
2. **Major — spec §10.2; P Task 3: rerun authority is narrowed.** The spec says to take fresh F2P rerun results on disagreement; that can hide failed/missing P2P evidence. The edited plan gives no credit to inconsistent aggregate evidence and retains reruns as diagnostics. **Smallest verification:** a patch that emits all-pass IDs but exits nonzero must earn zero; the spec owner must accept this stricter rule.
3. **Major — spec §§8, 10, 11; P Tasks 8/12: review hashes are not comparable.** The service sees an agent-supplied textual diff; grading hashes actual source contents. The plan reports comparison as null, rather than false equality. **Smallest verification:** commit changes locally before requesting review and show that the reviewed text may differ from the collected tree. Restoring the specified equality metric requires a shared trusted snapshot protocol; it was deferred with check execution.
4. **Major — spec §§8, 16: HTTP response generation is not delivery evidence.** A persisted service reply can be lost before the solver observes it. The plan exports actual agent trajectory observations as policy data and keeps the service log as audit. **Smallest verification:** drop a response after the server persists it; confirm the undelivered content does not enter policy-visible messages.
5. **Major — P Task 8: persistence APIs are verified; deployed crash recovery is not.** A single Modal container plus serialized Volume commits is a pilot topology, not proof of linearizability across replacement/deployment overlap. **Smallest verification:** ask, redeploy/terminate the container, retry the same request ID and freeze; compare one reply, one budget debit and stable hashes. If this fails, run the same service on the already-required VM rather than adding another storage product.
6. **Major — P Tasks 4/6/10: image/runtime reproducibility is not established by the existing smoke.** The smoke lacks the hardened collector and real historical dependency environment. Compiled extensions, legacy pytest/JUnit IDs, offline fixtures and editable paths vary by revision. **Smallest verification:** run base and gold on each selected pinned image, check imported package paths, check every exact test ID and exercise a root file-artifact round trip. Reject incompatible candidates rather than silently dropping regression IDs.
7. **Major — P Tasks 4/5; spec §§9.3, 13: reachability checks are bounded.** Deleting the old git database blocks known future-object retrieval, but a few distinctive-line searches are not a complete scan for copied solutions, cached patches or memorization. **Smallest verification:** `git cat-file -e` for the actual gold SHA plus a planted solution file outside the repository; expand the image audit if that planted file is missed. Do not claim the task is unseen by a model.
8. **Major — P Tasks 9/11/13: worker restart recovery is unexecuted.** API signatures and offline branch tests cannot prove a user systemd process survives service restart or that Modal results are ingested afterward. **Smallest verification:** interrupt the worker during one actual trial, retain the unit journal and Temporal history, and require exactly one launch plus a completed/exported record. Whole-VM loss is deliberately not claimed as transparent continuation.
9. **Major — spec §§6, 22; P Tasks 6/10: current GitHub issue bodies need not equal the issue as originally filed.** The normal REST response can include edits made after resolution. **Smallest verification:** inspect created/updated timestamps and source history for the chosen issue; archive retrieved text and retrieval time. If original text cannot be established, label it as retrieved rather than claiming historical fidelity.
10. **Major — latest spec withholding rule; P Tasks 1/6: substring checks do not prove semantic removal.** The code verifies verbatim provenance and literal excerpt absence/title retention; a paraphrase may still reveal a removed fact, or too much context may be removed. **Smallest verification:** human review of natural/withheld text and spans, plus a paired hidden-condition run. These are authored variants of the natural issue; do not claim natural underspecification alone caused the result.
11. **Minor — P Tasks 4/13: provider/model and deployment endpoints remain conditional.** No provider model call, VM creation, Temporal binary download or Modal deployment was performed by this review. **Smallest verification:** one bounded request per configured provider; verify the pinned Temporal CLI archive exists; deploy/probe the stakeholder; then one actual task. Record exact resolved versions in the lockfile and run metadata.
12. **Minor — spec §7; P Task 12: dataset.toml is not verified as a Harbor interface.** The installed harness has its own dataset/package models; the original TOML generator also left orphan table entries on updates. The plan now uses an explicitly swesim-owned JSON index and runs concrete Harbor task directories. **Smallest verification:** if publishing a Harbor dataset later, validate against Harbor's actual dataset manifest model before advertising compatibility.

## Cut or deferred items and the reason

- Executable stakeholder checks and a general agent tool loop: pay for persisted state, bounded requests and reliable grading. Diff-only review remains explicit and inspectable.
- Third scenario, more model tiers, non-pytest source support, DeepSWE importer, multi-step/combined PR tasks and complex frontend: protect the two source paths and the reviewable example.
- Full VM-loss recovery, automatic semantic labels, trusted review/submission equivalence and broad ranking claims: none has the required independent evidence within the trial window.
- A 5,000-line minimum and CodeClash-style tournaments: [CodeClash](https://github.com/CodeClash-ai/CodeClash) evaluates iterative competitive objectives. It does not establish a minimum diff size for a useful feature task. The adopted 200–1,500 source-line filter is a screening prior, with implementation difficulty still measured through agent runs.

No required milestone was waived. One task plus controls, a real interactive episode, the tracked runnable package, docs and laptop-off operation remain the minimum deliverable floor; the repo-only source and paired-profile evidence remain explicit completion requirements. Unfinished source discovery must remain unfinished in PLAN.md rather than being replaced with a manually chosen PR.

## Remaining questions a reviewer of the finished project would ask

- Which actual task requires a consequential design decision, and which baseline shows its coding difficulty rather than merely missing information?
- Which facts come from the original report, later thread, deliberate withholding or human repair? Can each be traced to the correct source version?
- Which attacks actually ran, did their patches apply, and which incorrect patch still earned credit?
- What is the tested residual risk from running source code inside pytest's process?
- Can I rerun the example from a fresh clone using only the README and declared credentials?
- How many candidate PRs were rejected for missing fixtures, unsupported environments, weak tests or insufficient ambiguity?
- Can the same request ID or a worker restart duplicate a reply, budget debit, solver launch or score record?
- Which model/profile/purpose cohorts have enough attempts for the reported k? Which traces are still unadjudicated and excluded from training-ready exports?
- Did a service reply reach the policy, or only appear in the service audit? What evidence supports each failure label?
- Does the live page show observed events, and is delayed agent visibility clearly labeled?
