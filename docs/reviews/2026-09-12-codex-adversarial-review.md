## Verdict

**Ship with changes.** As written, the reward file is rejected by Harbor, collection can execute agent-controlled code after network restrictions are relaxed, and validation permits a known tamper control to receive positive reward. The spec also mixes incompatible deployment and transcript-collection paths and lacks enough recorded inputs to reproduce stakeholder behavior. Fix those errors, establish the SWE-bench path end to end, then demonstrate the same pipeline discovering, creating and running a task from a GitHub repository URL without a required operator-selected PR. Production infrastructure, multiple providers, and DeepSWE import are lower priority than those two source paths and an inspectable stakeholder interaction.

## Blocking findings

**B1 — blocking — §10: the specified reward file cannot be parsed.** S:271–275 includes a string `outcome` and list `integrity_signals` in `reward.json`; H/verifier/verifier.py:89–122 explicitly rejects every nonnumeric value. An in-memory call to the actual parser raised `VerifierOutputParseError` first for `valid-correct`, then for an empty list when the string was removed; a numeric-only dictionary passed. **Change:** put only finite numeric metrics in `reward.json`, and put outcome, evidence, and signals in a separate report; this replaces an invalid format and adds no feature scope.

**B2 — blocking — §§9, 10, 13, 14: collection reopens a route to the public solution.** S:225–230 restricts the agent phase but does not restrict the environment baseline, then runs a commit against agent-controlled Git state. Harbor defaults the baseline to public and restores it before collection: H/models/task/config.py:247–252, H/trial/trial.py:264–279, H/trial/single_step.py:38–50; an offline context-manager probe confirmed `allowlist → public`. An agent can install a pre-commit hook that retrieves a known public fix when collection commits, after the solver budget and network restriction have ended; this attack was not executed, but the enabling call order is verified. **Change:** keep a restrictive baseline through collection, prebuild installation dependencies, and disable repository hooks/config-driven execution during trusted collection; pay for testing this by cutting a model comparison, not by building another provider.

**B3 — blocking — §§7, 10, 22: a successful reward hack can qualify a task as valid.** S:167–169 accepts a tamper patch if it is either zero-scored **or flagged**, while S:267–275 makes flags diagnostic and grants reward solely from passing tests. Thus a deliberately incorrect patch that forges passing outcomes can score one, be flagged, and still satisfy validation; unprivileged execution and exit-status agreement do not stop a self-consistent forged report. **Change:** every control explicitly designated as an incorrect exploit must receive zero or cause task rejection, independently of its flags; keep benign test/config edits diagnostic, and exercise one root-hook/report-forgery control before expanding the attack catalog.

## Major findings

**M1 — major — §§2, 4, 8–11, 14, 16, 20: there is no single executable topology.** S:35–38 excludes Modal, S:67–71 uses Docker/GCP plus a sidecar, S:181–219 uses a hosted service, and S:337–347 selects Modal and rejects local graded runs; S:225–227 and 274 still collect a sidecar ledger that §8 says must never be an agent artifact. These are verified contradictions, not hypothetical deployment failures. **Change:** choose one topology and one transcript join path throughout; a sidecar on a suitable Docker host is valid, while hosted service is a workaround for the selected Modal backend, not an architectural requirement—remove the alternate deployment from the deadline scope.

**M2 — major — §§5, 9, 11, 22: `full` can publish author-only material.** S:95–97 permits author-only facts, but S:87, 232–233 and 298 put every ledger fact in the full brief, contradicting S:204–206 and 443–444. No model validator prevents an author-only fact from carrying a contract-test link (M:71–77). **Change:** construct full instructions from stakeholder-visible contract/reproduction facts only, keep evaluator secrets outside all stakeholder prompts, and add a small profile-leak check; remove optional persona variation to pay for it.

**M3 — major — §§5, 7, 8, 11, 16: the normalized record omits inputs needed to execute and reproduce a scenario.** M:56–62 has neither Dockerfile content nor an asset reference for `kind=dockerfile`; M:101–107 lists filenames without a bundle root/hash; M:129–145 has no budget, event trigger, stakeholder model/prompt version, or run-config reference despite S:75 and 145–147. The actual model accepted duplicate fact IDs, dangling links, an empty test contract, an empty oracle, a traversal-shaped ID, and missing natural brief, and silently discarded supplied `budgets` and `events`. **Change:** add a small validated asset manifest and a versioned run/stakeholder config, reject unknown fields and invalid references, and either define one review trigger or remove event-based disclosure; cut extra source stubs instead of introducing a general workflow language.

**M4 — major — §§7, 10: no-op zero does not prove the historical bug is tested.** Under S:257–258 an empty submission scores zero before tests run, so `nop=0` can coexist with ineffective tests; M:101–120 also permits no target tests and empty lists of all negative controls. Although S:166 says to confirm base failure, the required evidence and the distinction from invalid-submission failure are unspecified. **Change:** record actual expected F2P failures and P2P passes on the base, require nonempty target tests and explicit negative-control minima, and verify exact expected test IDs/statuses; reuse one control run per identical contract instead of repeating all controls across prose-only conditions.

**M5 — major — §§8, 10, 11: agent-induced errors can disappear from reported performance.** S:279–281 retries/excludes evaluator, collection, and simulator failures without an attribution rule; submitted code can terminate the test process or create resource exhaustion, and API requests can intentionally trigger a service failure. That would game the denominator even without earning a positive individual reward; no successful exclusion exploit has been run. **Change:** solver timeouts, invalid outputs, and failures caused by submitted code remain failed attempts; reserve exclusion/retry for externally evidenced infrastructure faults, retain the original attempt lineage, and report unresolved attribution separately—replace the current blanket exclusion rule.

**M6 — major — §§8, 10, 16: the stakeholder protocol does not define a reproducible episode boundary.** S:187–219 gives tokens and two endpoints but no binding to scenario hash/condition/attempt, atomic budget accounting, request idempotency, end-of-episode freeze, or distinction between a generated reply and one actually delivered. Concurrent direct POSTs can test budget races, repeated requests can reroll answers, and late requests can change the transcript after the submitted patch was fixed; whether the future service permits these is unverified. **Change:** use one serialized session per trial, server-owned IDs/counters, cached responses for retried request IDs, and a terminal transcript snapshot; remove multi-trial distributed-service ambition rather than add a database platform.

**M7 — major — §§5–8, 11, 22: natural underspecification can silently become benchmark repair or authored intent.** S:121 and 158–163 allow annotator notes to seed facts, but the notes describe evaluation defects as well as missing user intent: D:89–91 describes insufficient output checks; D:157–161 describes private-name/warning dependence. A provenance enum without an excerpt/source reference on each fact cannot establish that a historical stakeholder required the synthesized behavior. **Change:** require a short source excerpt or explicit authored classification for each material fact, keep private implementation choices out of the contract unless justified, and do not claim independent extraction recall against notes also supplied as input; use manual checks on the demonstration tasks instead of a new semantic recall scorer.

**M8 — major — §§7, 8, 10, 11: LLM judgments still influence rewards and exclusions.** S:145–147 says code owns every reward-affecting decision, but S:206–208 lets an LLM decide which essential information is available, and S:307–316 uses semantic labels such as a relevant question receiving a wrong answer; §10 can then exclude that trial. A numerical reward calculation does not make these upstream decisions deterministic. **Change:** call the simulator stochastic, keep code-exact facts such as request counts separate from adjudicated labels, and require explicit human evidence before changing the trial denominator in the pilot; cut automated failure-cause classification before cutting raw traces.

**M9 — major — §§8, 9, 11: the three conditions change more than initial information.** Interactive agents receive command guidance, additional review executions, revision feedback and extra computation (S:197–211, 232–237), while the baseline conditions do not; common solver token/time limits and review-runtime accounting are absent from M and S:294–305. A changed worker-backed versus diff-only review mode also changes the experiment. **Change:** freeze the review mode and explicit budgets per run, describe results as the effect of the entire interaction treatment, and separate answer-only versus review-assisted interaction only if needed; pay for that comparison by removing a model tier.

**M10 — major — §§8–10: the review sandbox is not specified enough to preserve the claimed boundary.** S:197–202 requires isolation and no ledger access but says nothing about its network policy, credentials, file/path limits, process limits, or whether the reviewed patch matches the final submitted patch. An agent can request review of one diff and submit another, forge fixture output, or attempt network retrieval from its code inside the worker. **Change:** use the existing evaluation launcher to run one fixed review fixture against a content-hashed patch, without secrets/network and with bounded resources/output; if that cannot be validated, select diff-only review for every compared run and label it as such, removing the separate worker feature from the deadline.

**M11 — major — §§9, 10, 13: patch preparation, Git cleanup and overlays have no precise acceptance contract.** The collector uses Git inside `main` (S:225–227), while test cleanup only names hooks inside overlaid directories (S:261–270); root hooks, startup hooks, symlink/type changes, ignored new files, and a clean index after the oracle commit are not addressed. The pristine target checkout limits persistent environment modifications, but does not prove the patch represents the intended workspace or that overlay writes cannot be redirected. **Change:** define a small task-specific artifact/path policy, disable commit hooks, validate patch paths/types and expected output creation, restore trusted test discovery/configuration, and record the final patch hash; cut generic language support rather than demand universal untrusted-code isolation.

**M12 — major — §§12, 15, 20: the proposed selection loop can manufacture the requested model ordering.** S:323–324 uses the same models' success to select/re-profile tasks, and the plan then reports their gradient without a held-out calibration distinction; three attempts provide only coarse evidence per task. Cheap or small models are not guaranteed to be weaker on each selected task. **Change:** label task-selection runs as calibration, freeze accepted tasks/configs before fresh comparison attempts, retain selection/rejection history, and report counts plus component outcomes without a general ranking claim; reduce models before increasing the dataset to chase a desired gap.

**M13 — major — §§16, 18–20: the fully authored simulation can be absent from the delivered repository.** All generated tasks live under ignored `workspace/` (S:397 and .gitignore:1); `!workspace/registry.json` does not re-include a child of the ignored directory, as verified with `git check-ignore --no-index -v`. Existing code is a scaffold whose nine commands all exit 2 (`swesim/cli.py:13–31`), and there is no tracked authored task yet. **Change:** reserve a tracked example task/bundle plus a sanitized example run and executable run/author instructions; preserve this deliverable even if the third task, bucket integration, or extra dashboard screens are cut.

**M14 — major — §§5, 10, 15, 16, 22: post-training consumers cannot yet tell which exported material is safe to learn from.** The registry mixes scenario secrets, oracle material, facts, observations, and scored traces (S:105–115, 365–370), with no policy-view export, per-family split grouping, simulator validity marker, or linkage to exact prompts/tool observations and evaluator revisions. An RL team would need trustworthy rewards and episode isolation; an SFT team would need filtered trajectories rather than the entire debug directory. **Change:** export one simple episode manifest separating policy-visible messages from evaluator-only material, with config/patch/scenario hashes and a source-family ID; state that trainer-specific token/logprob integration and actual training are out of scope, and remove automatic bucket synchronization if necessary to pay for the manifest.

**M15 — major — §§6, 7, 19, 20: the requested GitHub repo-only path is not specified.** The author's latest steering makes SWE-bench the starting source and automatic task creation/running from a repository URL the second priority, with DeepSWE optional; S:149–153 only shows `--repo URL --pr N`, and S:409 only promises authoring from a PR URL. Candidate enumeration, a bounded search/attempt budget, optional rather than required PR selection, and the behavior when no valid task is found are absent. **Change:** define repo-only discovery feeding the same judge/spec/compile/validate/register/run stages, within one supported Python build profile, and demonstrate one run from that entry point; remove DeepSWE import and additional model tiers to pay for this required product path.

**M15 status after concurrent revision:** S1:126–150,173–178 now defines repository-only discovery and optional PR/issue selection, and the source enum was renamed accordingly. The remaining work is to bound candidate/build/model expenditure, specify the no-valid-candidate outcome, and demonstrate the path; do not require the operator to supply a particular issue or PR.

**M16 — major — new §7a: the idempotency key conflates distinct trials and does not prevent duplicate remote launches.** S1:222–227 keys activities by `(scenario_id, version, stage)`, which omits condition, model configuration and attempt; using that key for `run_trial` can collapse distinct trials, while losing the launch acknowledgement can cause a retry to start a second Harbor job. Temporal Activities can execute more than once after a worker failure, even if the first external operation completed ([official error-handling guide, “Make Activities idempotent”](https://docs.temporal.io/develop/python/best-practices/error-handling)); no launch/reconciliation implementation exists to verify. **Change:** assign a stable ID to each requested trial, distinguish a Temporal retry from a new experimental attempt, and return an existing job/result on retry; initially disable automatic launch retries until reconciliation works, and remove custom pipeline-funnel UI work to pay for that check.

**M17 — major — new §7a and §17: Temporal scope payment and concurrency bounds are not concrete.** S1:214–236 adds repository, scenario and matrix workflows, signals, heartbeats and a second direct execution path, but pays by moving DeepSWE/review work that was already stretch in S:427–428; §17 still retains the custom pipeline funnel Temporal is supposed to replace. A task queue alone is not a stated limit on candidate fan-out, concurrent activities, remote jobs or spend. **Change:** start with one pipeline workflow and coarse existing stage functions, explicit worker/job and candidate limits, and the Temporal UI for stage status; remove the custom funnel/visibility-API integration and extra workflow hierarchy before cutting task fidelity or the GitHub source path.

## Minor findings

**N1 — minor — §§1, 3: several positioning claims are inaccurate.** S:8–11 calls the original SWE-bench fully specified despite this project's rejected-issue premise; S:44 says it discards the thread although §6 uses its discussion-derived `hints_text`; S:45 calls Ambig-SWE agent-side only even though it introduces an interactive benchmark; S:49 conflates real-PR SWE-Gym with injected-bug generation. **Evidence:** S:121 and 128–135; [Ambig-SWE abstract](https://arxiv.org/abs/2502.13069); [SWE-Gym abstract](https://arxiv.org/abs/2412.21139). **Change:** distinguish one initial user request from one model/tool turn, and state the contribution as the authoring/validation workflow without categorical novelty claims; no new workstream.

**N2 — minor — §6: bucket and dataset statistics need exact predicates and revisions.** The 245 count requires `underspecified >= 2`, `false_negative == 2`, and `other_major_issues == 0`; the shortened B definition at S:130–131 yields 521 if its underspecification restriction is omitted. The 6,542/21,336 SWE-rebench snapshot at S:124 is not included with its query/revision, and the Pro 24% statement at S:125 comes from an LLM audit of sampled rollouts rather than a universal error rate. **Change:** record the existing filtering expression/data hash and qualify the audit, or omit incidental counts for stub sources; no additional collection needed.

**N3 — minor — §§8, 14, 21: some deployment facts are overstated or stale.** A host allowance does not itself establish routing from a container to a service bound to laptop localhost (S:187–189); Docker's kernel check can also return false on probe execution errors (H/environments/docker/docker.py:920–950), and §9 still calls the supposedly failed check unresolved. **Change:** record a reachable service URL and the actual probe result, distinguish CLI installation from a ready GCP fallback, and update the unresolved list using existing evidence; do not provision another provider just to resolve a documentation claim.

**N4 — minor — §§5, 8, 11, 16: reproducibility metadata is too informal.** Image tags and optional free-text dictionaries do not identify immutable image contents or a unique experiment, and temperature zero plus a recorded seed (S:209) does not establish deterministic provider responses. **Evidence:** M:56–62, 123–126, 129–145 and R/deepswe-task-example/task.toml:39 use no image digest field; no live stakeholder configuration exists. **Change:** record resolved image/model/package/prompt identifiers in the episode manifest and preserve actual replies; defer reproducible rerendering across providers.

**N5 — minor — new §7a: the proposed dev-server command loses state on server restart.** S1:228 uses bare `temporal server start-dev` while presenting durable recovery as a reason for adopting Temporal. The installed CLI's help explicitly states that executions are lost when the server dies unless `--db-filename` is supplied. **Change:** use a persistent local database file if restart recovery is demonstrated, keep large patches/traces as artifact references rather than Workflow payloads, and test one worker restart; this replaces default configuration and does not require Temporal Cloud.
