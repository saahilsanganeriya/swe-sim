## Verdict

**Ship with changes.** The three blocking Codex errors are genuinely fixed at the design level: `reward.json` is numeric-only (VERIFIED against H/verifier/verifier.py), collection no longer runs a git commit over agent-controlled state (a root tar collect hook replaces it, VERIFIED it executes no agent code), and incorrect-exploit controls must earn reward 0. But v2 introduces new problems while fixing old ones: the receipt and `app.tar` are written into `/logs/artifacts`, which Harbor makes world-writable, so the "trusted receipt" is agent-forgeable; the freeze-before-verifier ordering the session protocol depends on is not achievable because `harbor run` owns the verifier lifecycle; the partial-reward split leaves §10.3's outcome table keyed on "reward 1/0" while §10.5 makes reward continuous; `protected_paths` omits `sitecustomize.py`/`.pth`, reopening the import-time report-forgery path the threat model claims to bound; the multi-key non-binary `reward.json` silently disables Harbor's own pass@k helper; and the schedule (§20) is not creditable for one implementer in the remaining ~22 hours. The design is sound enough to build, but the schedule must be cut hard and roughly six correctness gaps closed before the reward-hacking and reproducibility claims are defensible. Blocking: 3. Major: 11. Minor: 9.

## Blocking findings

**BL1 — blocking — §9.1, §10.1, §10.2 step 1: the "trusted receipt" and `app.tar` live in an agent-writable directory.** S:377-389 has the root collect hook write `app.tar` and `collect.status` into `/logs/artifacts`; S:436-457 treats `collect.status` as the receipt and trust anchor. But Harbor makes `/logs/artifacts` world-writable (`chmod 777`, H/environments/modal.py:321-323; H/models/trial/paths.py:158-162), and in single-step separate mode the agent container is still alive during the main-pass download of `/logs/artifacts` (H/trial/single_step.py:41-47; the container is stopped only before the *sidecar* pass, H/trial/trial.py:1404-1414). A backgrounded agent process can `rm` the root-owned `app.tar`/`collect.status` (unlink needs write on the 777 dir, not on the files) and drop in a self-consistent forgery (fake tar plus a `collect.status` whose recorded sha256 matches it). The verifier re-runs the tests so this yields no *reward* advantage, but it means the receipt proves nothing about who collected — the spec's claim that the receipt distinguishes `collection-failure` from agent-invalid (S:454-457) and the commit's "trusted receipt" framing are false. **Change:** collect into a root-only path (`mkdir -m 700 /var/swesim-collect` owned by root at build) and declare it as a single **file** artifact `{source="/var/swesim-collect/app.tar"}`, which Harbor collects with `service_download_file` (no directory extractall, H/trial/artifact_handler.py:311-318) and uploads to the separate verifier at the same absolute path (H/trial/artifact_handler.py:189-213). That fixes both this and the directory-artifact-reliability motivation at once. **Pay for it:** free — it removes the `/logs/artifacts` dependency, no new scope.

**BL2 — blocking — §8 session protocol vs §4/§9.4 topology: freeze-before-verifier is not achievable.** S:325-327 says "The worker calls freeze before starting the verifier," and the whole late-mutation defense (S:531, G18) rests on it. But the topology (S:107, §9.4 separate verifier) runs the verifier *inside* `harbor run`: one `harbor run` call executes agent → collect → stop agent env → verifier → return (H/trial/single_step.py:38-55). The worker (S:104 `launch_harbor` → `await_result`) only regains control after `harbor run` returns, i.e. after verification. The worker therefore cannot freeze between agent-end and verifier-start. **Verified**: `SingleStepTrial._run` performs verification with no worker callback between phases. The security outcome is still fine (Harbor stops the agent container before the verifier, H/trial/single_step.py:49-51, so nothing can reach the session during verification), but the stated mechanism is wrong and, if implemented literally, the worker would call freeze far too late. **Change:** state the real invariant — the session is effectively frozen by agent-container termination; the worker freezes on transcript fetch after `harbor run` returns and binds `transcript_hash` + `reviewed_diff_sha256` then. **Pay for it:** free (documentation correction).

**BL3 — blocking — §10.3 vs §10.5: the outcome table and pass@k contradict the new reward definition.** §10.5 (S:485-503) makes `reward` continuous in [0,1] and introduces binary `success`, but §10.3's table (S:509-510) still defines `valid-correct` as "reward 1" and `valid-incorrect` as "reward 0," and §7 step 8 (S:275) defines pass@k success as `outcome in {valid-correct}`. Under partial credit a valid-incorrect attempt routinely has `reward` 0.4, not 0, so the table mislabels every partial solution and the denominator/numerator for pass@k is ambiguous. **Verified** internal contradiction. Separately, Harbor's built-in pass@k helper returns nothing for this reward file: H/utils/pass_at_k.py:44-51 requires exactly one reward key whose value is in `(0,1)` — the spec's `reward.json` has ~10 numeric keys and a non-binary `reward` (S:440-444), so `len(rewards) != 1` short-circuits and no pass@k is computed. **Change:** re-key §10.3 on `success` (valid-correct = success 1; valid-incorrect = success 0, any reward); state explicitly that swesim computes pass@k/pass^k itself over `success` and does not use H/utils/pass_at_k.py. **Pay for it:** free (both are edits to already-present text).

## Major findings

**MA1 — major — §10.2 step 2, §10.4: `protected_paths` omits `sitecustomize.py`/`.pth`, reopening import-time forgery.** S:462-467 protects `conftest.py`, `pytest.ini`, `tox.ini`, `setup.cfg`, `pyproject.toml`, CI config, lockfiles — but not `sitecustomize.py`, `usercustomize.py`, or `*.pth`, all of which Python auto-imports at interpreter startup before any test code. The DeepSWE reference scan list explicitly flags `sitecustomize.py` (references/deepswe-task-example/tests_test.sh:25). An agent can add a repo-root `sitecustomize.py` (applied because it is not dropped) that monkeypatches the JUnit writer or `pytest`'s reporting; since it is imported by *every* pytest process, the per-process re-run defense (S:476-478) imports it too. **Change:** add `sitecustomize.py`, `usercustomize.py`, `**/*.pth`, and `.pth`-bearing dirs to `protected_paths`, and run pytest with `-P` / a clean `PYTHONPATH` that excludes the repo root as a site dir. **Pay for it:** none; it is a list addition.

**MA2 — major — §10.2 step 4: the "random JUnit path not known to the code under test" defense is defeatable by introspection.** S:473-474 relies on a per-run JUnit path "not known to the code under test in advance." But pytest receives that path as `--junitxml=` / `PYTEST_ADDOPTS`, both readable by in-process code via `sys.argv` and `os.environ`. Malicious product code can locate and overwrite the report. Combined with MA1 this is a working forgery. **Verified** the reference passes the path via `PYTEST_ADDOPTS` (references/deepswe-task-example/tests_test.sh:34-35). **Change:** stop relying on path secrecy; parse results from a channel the test process cannot address (e.g. a pytest plugin loaded by the grader that writes outside the test process's view, or reconcile against captured stdout markers), and keep MA1's startup-hook protection. Document that in-process forgery remains a residual (§10.4 already concedes this — good — but the mechanism it credits is weak). **Pay for it:** cut the live-streaming dashboard (MA9).

**MA3 — major — §9.1 collect hook user is not pinned to root.** S:377-379 asserts the hook is "run by Harbor as root," but Harbor defaults a collect hook's user to the *service container's default user* (H/models/task/config.py:745-749; the hook is invoked with `user=hook.user`, H/trial/trial.py:1343-1348). During collection the environment's `default_user` is `None` (H/environments/base.py:190; the agent-user context is scoped to the agent phase, H/trial/trial.py:538), so the hook runs as the image's default `USER`. That is root for stock SWE-bench images, but the swesim agent Dockerfile (S:403-416) creates an `agent` user and does not state its final `USER`; if any base image sets `USER agent`, the hook runs as `agent` and the "only root-owned binaries run" guarantee collapses. **Change:** set `[[verifier.collect]] user = "root"` explicitly and assert the agent image's default `USER` is root. **Pay for it:** none.

**MA4 — major — §8 patience + no-drip collapses `interactive` toward `full`.** S:331-333 ("broad legitimate questions may receive broad answers, no forced drip") plus S:337-352 (asking is never reward-penalized; cost is a code-owned patience budget the environment reward ignores) mean the reward-optimal policy is to ask one maximally broad question, receive all `on-request` facts for one `question_cost`, and then solve. `interactive` then equals `full` minus author-only material (which `full` also lacks). The intended difficulty gradient across tiers compresses, and the measured "interaction effect" degenerates to "did the model ask at all." **Change:** either accept and state this explicitly (the experiment measures willingness-to-ask, not calibrated questioning), or make `full` genuinely distinct by withholding `on-request` facts from `full` too and forcing the interactive path for them; and report interactive results conditioned on questions-asked so the one-broad-question case is visible. **Pay for it:** covered by cutting a model tier if you add the conditioning analysis.

**MA5 — major — §6 non-derivability screen selects on the dependent variable and is underpowered.** S:214-218: after calibration, "a task the frontier tier passes in `hidden` on all attempts is moved out of the interactive comparison set." With k=3 calibration attempts (S:549), 3/3 hidden passes is a noisy estimator, and screening the comparison set on frontier hidden-difficulty biases the retained set toward large `full`−`hidden` gaps — i.e. you select for the effect you then report. The calibration/comparison split (S:545-547, good) prevents *reusing* selection runs as results but not this selection bias. The screen also does not remove tasks the frontier fails in `full` on all attempts (unsolvable-even-with-info), which deflate the interaction effect symmetrically. **Change:** raise calibration k for the screen, screen both tails (drop hidden-trivial *and* full-impossible), and report the comparison set as a biased, calibrated sample with the screen thresholds stated; make no cross-model ranking claim (already promised, S:550). **Pay for it:** none (methodology + reporting).

**MA6 — major — §6 pool-B clarification-vs-repair classification is not implementable as specified, and the annotations argue against it.** S:196-197 admits pool B "only after the judge classifies the test's unstated assumption as a stakeholder choice (clarification) rather than an evaluator defect (repair)." I read the pool-B (`underspecified>=2, false_negative==2`) rows: their `false_negative_notes` overwhelmingly describe *test overfitting* — e.g. astropy-14578 "tests fail for the first perfectly reasonable solution (auto-converting objects)," astropy-13234 "changes not discussed in the issue so any reasonable solution may miss these," astropy-14590 "tightly coupled to implementation." These are evaluator defects, not stakeholder choices; turning them into a "clarification" means the stakeholder must voice the exact implementation the unfair test demands — which is the very "natural underspecification becomes benchmark repair" failure Codex M7 warned about. The judge criterion is an LLM/human judgment with no crisp predicate. **Change:** for the first version, prefer pool A (109 rows, mostly `false_negative<=1`); admit a pool-B task only with a human-written justification that the withheld fact is a genuine product decision *and* the F2P test does not encode an arbitrary implementation detail; record the operation as `evaluator-repair` when it is one and exclude such tests from the scored contract. **Pay for it:** none; narrows source scope.

**MA7 — major — §5.1/§5.2 vs M: the hardened schema is unimplemented and `models.py` contradicts it.** S:118-179 specifies `extra="forbid"`, an `assets` manifest with sha256, `RunConfig`, per-fact `source_excerpt`/`authored_rationale`, `contract.protected_paths`/`expected_base`/`expected_gold`/`groups`, and `controls` with `expected_success`/`expected_reward_max`. `models.py` has none of these: no `extra="forbid"` (M:129-145), `Contract` still uses `hidden_test_files`/`overlay_paths`/`review_fixtures` (M:101-107), `Controls.Patch` carries inline `diff` not asset refs (M:110-120), there is no `RunConfig`, `assets`, `groups`, or `spec_hash`, and `Discovery` still has `VOLUNTEERED_AT_EVENT` (M:45) where the spec uses `volunteered-at-review` (S:312). An offline `ScenarioSpec.model_validate` (per Codex, still true of M) accepts duplicate ids, empty contracts, `id='../outside'`, and silently drops unknown fields. **Verified** M is the pre-review schema. This is expected pre-implementation, but the validators the spec's integrity claims depend on do not exist yet, and the enum drift (`volunteered-at-event`) will break the disclosure logic. **Change:** implement the §5.1 model with validators as the first evening task (it gates compile/validate); reconcile the `Discovery` enum. **Pay for it:** already first on the §20 critical path.

**MA8 — major — §17/§14 vs Codex M17: the dashboard re-adds the custom visibility integration M17 said to cut.** §0 claims M17 is resolved by keeping Temporal thin, but §17 (S:650-652) now builds a FastAPI app reading "Temporal's visibility API" plus live-streamed stakeholder chat, and §2 item 7 (S:61-63) promotes it from "minimal dashboard" to a two-page live UI. That is precisely the custom pipeline-funnel/visibility work Codex M17 told you to drop in favor of the Temporal UI. It is also the largest single piece of new afternoon scope. **Change:** revert to Harbor's viewer + the Temporal UI for state, and one static post-hoc episode page reading job directories; drop live streaming and the visibility-API integration. **Pay for it:** this *is* the payment for BL/MA fixes and the schedule.

**MA9 — major — §17 live stakeholder streaming is speculative and self-hedged.** S:640-644 concedes agent actions can be shown live "only if Harbor's output subscription hooks (`trial.py` logging callbacks) can be wired to the worker in time." Harbor exposes trial lifecycle hooks (H/trial/hooks.py:17-27: START/AGENT_START/AGENT_END/VERIFICATION_START/END) but installed agents write their trajectory only at run end (H/agents/installed/mini_swe_agent.py:685-699), and the worker drives Harbor as an opaque `harbor run` subprocess (S:104), so there is no in-process hook surface for the worker without embedding Harbor as a library. **Change:** cut live streaming entirely; poll the stakeholder service transcript endpoint for a near-live chat view only, and show the agent timeline post-hoc. **Pay for it:** subsumed by MA8.

**MA10 — major — §20 schedule is not creditable for one implementer in ~22 hours.** With ~25h wall to the 16:00 deadline, the evening slot (S:682-687) asks for the full grader (member-filtered tar extraction, pristine content-diff, case-folded protected-path globs, group partial credit, exact-id JUnit parse with disagreement re-run, chown-and-drop-privilege) *and* `patch-agent` *and* compiling+validating a real SWE-bench task with four controls on Modal *and* the stakeholder service (FastAPI, sessions, patience state machine, structured LLM calls, shims, container-start token injection) *and* one interactive episode — each of the grader and the service is itself a full day. The morning adds two Temporal workflows, the whole `swebench-annotated` pipeline, *and* a live GitHub clone-install-run-strip build on an unknown repo (notoriously fragile), plus score/export/restart. The afternoon runs 2 tasks × 3 conditions × 2 models × k=3 = 36 Modal SWE-bench trials whose image pull/run times the spec itself lists as unknown (S:714), plus tracked example, dashboard, docs, and the presentation. **Change:** apply the cut list below; verify mini-swe-agent-as-agent-user first (MA11) because the interactive deliverable depends on it. **Pay for it:** see cut list.

**MA11 — major — §21: mini-swe-agent running as the `agent` user is unverified and on the critical path, with a concrete failure mode.** S:706-707 lists this as unresolved. Harbor's install for mini-swe-agent runs `curl … | sh` and writes `$HOME/.local` and `$HOME/.bashrc` as the agent user (H/agents/installed/mini_swe_agent.py:644-672), executed under `with_default_user("agent")` during setup (H/trial/trial.py:456-459). Modal's exec wraps commands as `su <user> -s /bin/bash -c …` (H/environments/modal.py:336-341) — a **non-login** `su`, so `$HOME` may remain root's `/root` (agent cannot write) rather than resetting to the agent's home, and the §9.3 Dockerfile (S:403) never states `useradd -m`, so the agent may have no home dir at all. If either holds, the install fails and there is no interactive episode. The visible smoke runs used oracle/nop (no install) and did not set `[agent] user` at all (J/smoke-oracle-allowlist config has no `[agent].user`). **Change:** in §9.3 create the agent with a home dir and pre-seed uv/mini-swe-agent into a world-readable toolchain during image build so no per-run user install is needed; run the one-shot verification probe before building the service. **Pay for it:** none; de-risks the deliverable.

## Minor findings

**MI1 — minor — §0 vs §9.1: stale changelog.** §0 (S:11-12) still says "collected as a tarball by Harbor under an allowlist baseline," but §9.1 (S:377-389) replaced Harbor directory collection with a collect-hook tar and explicitly rejects Harbor's directory-artifact path. Update §0.

**MI4 — minor — §14 baseline claim vs the smoke's own baseline.** The B2 fix (allowlist baseline governs collection) is verified from source, but the visible smoke ran with `[environment] network_mode="public"` (public baseline), so it does not itself demonstrate collection under an allowlist baseline. **MI5 — minor — §9.4: the unprivileged test user is never created.** §10.2 step 4 (S:470-472) runs pytest "as the unprivileged user," but §9.4 (S:418-423) does not create such a user in `tests/Dockerfile`. Add `useradd` and confirm the grader's `su` target exists.

**MI7 — minor — §7 step 8 / §2: "minimal dashboard" wording is now inconsistent.** S:278 still calls it "the minimal dashboard" while §2/§17 describe a two-page live UI. Pick one.

**MI8 — minor — §5.2/§8 budget terminology drift.** RunConfig replaced `question_budget`/`review_budget` with `patience_profile` (S:176), but §8's session protocol still speaks of "counters" and "over budget returns a fixed refusal" (S:322-323) and §2 says "the budgets." Unify on patience.

**MI9 — minor — §9.1 collect hook PATH-hijack residual.** The hook runs bare `tar`/`du`/`sha256sum` (S:381-383). If root's `PATH` ever contains `.` or an agent-writable dir, an agent-planted `tar` in the CWD (`/app`) could run. ## Experimental-design findings

- **ED1 (MA4):** No-drip + code-owned patience with zero reward cost makes the reward-optimal interactive policy "ask one broad question, get everything," collapsing `interactive` toward `full` and flattening the intended difficulty gradient. The "choice among reasonable alternatives" facts (S:204-208) still surface in one broad answer.
- **ED2 (MA5):** The hidden-condition empirical screen (S:214-218) selects the comparison set on the frontier model's hidden performance — selection on the dependent variable — and is underpowered at k=3. It also screens only the hidden-trivial tail, not the full-impossible tail. This is a milder version of Codex M12 that the calibration/comparison split does not remove; it biases the reported `full`−`hidden`/`interactive`−`hidden` gaps upward.
- **ED3 (MA6):** The pool-B clarification-vs-repair judgment is not a crisp predicate and, per the actual annotations, most pool-B `false_negative==2` rows are test-overfitting (evaluator defects), so admitting them risks manufacturing contract requirements from test internals. Not implementable as an objective LLM gate; prefer pool A for the first version.
- **ED4:** `full` is called "a baseline, not a ceiling" (S:543), yet with author-only material excluded from every condition, `full` *is* the practical ceiling of disclosable information; the experiment cannot distinguish "interaction helped" from "the model just needed the facts." State this bound.
- **ED5:** k=3 with two tiers on two tasks yields pass^k over 3 attempts — too few for any confidence interval; §11 already says "counts, not CIs" (good), but the difficulty-gradient claim across tiers rests on ≤2 tasks and will not be statistically distinguishable. Frame it as an existence demonstration, not a measured gradient.
