Design explainer · 2026-09-12

swesim: underspecified issues in, multi-turn gradable SWE simulations out

SWE-bench, Terminal-Bench and DeepSWE grade one shot against a fully specified instruction. Real issues arrive underspecified, and the discussion thread is where a maintainer resolves what they actually wanted. SWE-bench Verified filtered those issues out as noise. swesim treats them as the signal: the original issue is the brief, the resolution lives with a simulated stakeholder the agent can talk to, and the PR's tests are the contract.

What existing benchmarks leave out

Every current benchmark collapses the messy middle of software work into one instruction. The thread between "here is a bug" and "merged" is where requirements actually get decided, and it is exactly what is thrown away.

SWE-bench · DeepSWE · Terminal-Bench

One shot

Verified went further and removed issues that were underspecified or had over-specific tests, which made the benchmark cleaner and quietly deleted the hardest real-world skill.

How work actually happens

A thread

The clarifications, the constraint a reviewer insisted on, the interface name chosen in review: all real, all recorded, all unused by benchmarks.

Labels are seeds, not truth. For every selected instance the pipeline records four answers: what is actually missing, whether the original discussion supplies it, whether it is a legitimate behavioral requirement, and whether the evaluator accepts alternative correct implementations. Where a test encodes an incidental private helper name, that is an evaluator repair, recorded as such, not a fact for the stakeholder to reveal.

The pipeline

Nine stages, one CLI. Every source produces the same normalized record, and everything after spec consumes only that record. That single seam is what makes new sources, including fully authored novel tasks or private repositories, a matter of writing one producer.

Anatomy of one scenario

Illustrative record for SWE-bench instance sympy__sympy-13581, a pool A task. The issue asked for one simplification; the annotators flagged that it never says why or how; the reviewer stated the real constraint during review. Fact wording below is drafted from the real thread and is exactly what the spec stage would produce for a human to edit.

Brief · profile natural · provenance original-issue
Mod(Mod(x + 1, 2) + 1, 2) should simplify to Mod(x, 2)

Currently it does not simplify. Expected: Mod(x, 2).
What the annotators said was missing

"Identifies the problem and a specific example of the desired behavior. However, it lacks details on why the simplification is not occurring and does not provide the expected general rule." Severity 2 of 3. Difficulty: 1 to 4 hours.

Persona · derived from thread

Core maintainer. Terse, mathematically precise, answers exactly what is asked, pushes back on overreach. Volunteers nothing until review.

Ledger · what the stakeholder knows
F1
Nested Mod with the same modulus should collapse: Mod(Mod(A, c) + B, c) == Mod(A + B, c).
behaviorpr-threadon-request
tests: t1, t2
F2
Not every operation commutes with Mod. The simplification must check the type of the inner term and apply only to additive structure.
constraintpr-reviewon-request
tests: t3
F3
Different moduli must not be merged; Mod(Mod(x, 3) + 1, 2) stays as is.
behaviorannotator-noteon-request
tests: t4
F4
The existing Mod.eval in sympy/core/mod.py is where distributive rules live.
contextissue-threadrepo-derivable
tests: none
Contract · verifier owned

FAIL_TO_PASS: the PR's new tests in test_arit.py, copied into the verifier image. PASS_TO_PASS: the existing module tests. Review fixtures: two smaller cases, never the contract.

Controls · executed by validate
✓oracle = gold patch✕nop✕wrong: merge any nested Mod✓alt-correct: rewrite via Add.args⚠tamper: skip marker, conftest exit

Discovery paths are the honesty mechanism. A fact tagged repo-derivable can be found by reading the code, so an agent that never asks is not penalized. A fact tagged on-request is absent from the repository and required by a test, so asking becomes necessary rather than rewarded. A fact tagged author-only may never be required by the contract.

Runtime topology

Four isolated places, one leak boundary. The hidden ledger never enters the agent's container. The agent's network allowlist contains only its model API and the stakeholder service, so the public fix cannot be fetched from GitHub. Grading happens in a container the agent never touches.

agentstakeholderverifierneutral · holds no secrets
Why not a compose sidecar
Harbor on Modal and Daytona disables network allowlists when a compose file is present, and Docker Desktop on the dev Mac fails the egress kernel check. A hosted service keeps the boundary and works on any single-container provider.
Why grade a patch, not a container
The agent controls everything in its sandbox. The verifier trusts only a binary diff against the compiler-recorded base commit, applied to a pristine checkout, with its own copies of tests and runner config. Adopted from DeepSWE v1.1.
Why strip git history
On SWE-bench Pro, Claude Opus 4.6 and 4.7 ran git log --all and copied the gold patch in over 12% of rollouts. Our images check out a real branch at base, drop remotes, delete non-ancestor refs, expire the reflog and gc.

Three conditions, one contract

Every task compiles to three Harbor tasks that share the environment image, the contract and the grader. Only the instruction and the stakeholder session differ. Comparing them is the experiment.

The agent sees: the natural brief plus every ledger fact written out. Stakeholder: none; the shims report no stakeholder is available.
Purpose: a baseline with requirements upfront. It is not a ceiling: an agent can do better with feedback than with a complete spec, so the comparison is between conditions, never against a presumed maximum.
The agent sees: the natural brief only. Stakeholder: none.
Purpose: the effect of withholding information with no recovery channel. This is the setting the underspecified issue put real contributors in before they asked.
The agent sees: the natural brief plus one paragraph describing ask-user, request-review and the budgets. Stakeholder: live, seeded, temperature 0.
Purpose: how interaction recovers from incomplete information, at what cost in questions, review rounds and simulator tokens.

Reading a failure

Labels are assigned from evidence in the transcript and ledger, and unresolved is a legitimate answer. Nobody gets to call a failure "the simulator's fault" without the transcript showing the question and the withheld answer.

ObservationLabel
Relevant question asked; required answer withheld or wrongsimulator failure
Clear ambiguity; agent assumed incorrectly without askingpotential agent failure
Requirement delivered clearly; implementation violates itlikely implementation or retention failure
Correct result without clarificationsuccess without clarification
Trace cannot establish the causeunresolved

Grading and what it resists

Reward is binary correctness on the hidden contract, computed in the separate verifier. Everything else is a component or a signal, reported so a reviewer can see partial progress and tampering attempts without either one changing the reward.

reward.json
{
  "reward": 1,                 // 1 only if every F2P and P2P test passed
  "f2p_pass_fraction": 1.0,
  "p2p_pass_fraction": 1.0,
  "outcome": "valid-correct",
  "integrity_signals": []      // recorded, never zeroing on their own
}
Outcome classes · all counted, none hidden
✓valid-correct ✕valid-incorrect ✕agent-invalid-submission ⟳collection-failure ⟳simulator-failure ⟳evaluator-failure

Only the three infrastructure classes are retried, once, by fixed policy, and excluded from pass rates with their counts shown. An agent that submits nothing, or deletes its work, is agent-invalid-submission and stays in the denominator.

Residual, stated: the package under test executes inside the test process. That is inherent to unit-test grading and is documented rather than claimed away.

Orchestration, and Temporal

Stages are idempotent functions of workspace state with explicit status in registry.json, so a durable workflow engine such as Temporal can wrap them later with each stage as an activity and the pipeline as a workflow. Adding it before the deadline adds a server, workers and determinism rules without adding a deliverable; the file-backed design is what makes the migration cheap.

What ships by the presentation, and what we will not claim

Ships
  1. The nine-stage CLI over one normalized record
  2. Two to three tasks through the full path, three conditions each
  3. Stakeholder service with grounded review (fixture sandbox if time; diff-only marked unverified otherwise)
  4. Separate verifier, outcome classes, integrity signals
  5. All five control classes executed and recorded per task
  6. Registry that grows by construction; traces synced
  7. Dashboard: funnel, task card, run matrix, trial explainer
  8. README, grading document, architecture and realism document
We do not claim
  • That any model has not seen a task. A strong full-spec baseline measures performance under that spec, not memorization.
  • That interaction reward is solved. Interaction is measured and reported, not rewarded.
  • That the simulator is realistic beyond what its transcripts show.
  • That importers marked stub work.
  • That sweep durations or pass rates generalize beyond the recorded agent, model, harness, simulator and budget.
  • That the verifier is immune to arbitrary code: the package under test runs in the test process.
