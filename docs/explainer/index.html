Design explainer · spec v2.1 · 2026-09-12

swesim: underspecified issues in, multi-turn gradable SWE simulations out

SWE-bench hands an agent the issue as the reporter wrote it and grades a patch with the fix's tests. Many of those issues are underspecified; the discussion that resolved them ships in the dataset but is never shown to the agent. SWE-bench Verified removed such issues as noise. swesim keeps them as the brief, puts the resolution with a simulated stakeholder the agent can talk to, grades with the fix's tests in a clean container, and is a pipeline that produces such tasks from SWE-bench's human-annotated pool and from any GitHub repository URL.

Runtime Harbor 0.23 on Modal Orchestration Temporal, kept thin Reward binary correctness, controls executed Interaction measured, never rewarded Status spec v2.1 after two adversarial reviews · Modal execution verified end to end with a real agent

A gentler walk-through for newcomers is at primer.html. The full spec is linked in the footer.

What existing benchmarks leave out

Every current benchmark collapses the messy middle of software work into one instruction. The thread between "here is a bug" and "merged" is where requirements get decided, and it is exactly what is not shown to the agent.

SWE-bench · DeepSWE · Terminal-Bench

One shot

Verified filtered out issues rated underspecified and tests rated unfair. Cleaner exam, and it deleted the skill of working with an unclear ask.

How work actually happens

A thread

Which exception, which message, which of two output shapes, what to do for an input the reporter couldn't share: decided in the thread, recorded on GitHub, unused by benchmarks.

Complexity comes from the repository source, not from pool A. Pool A's gold patches are small: median 6 source lines in one file. Measured over 6,458 merged PRs across the SWE-bench and DeepSWE upstream repos, the "complex enough" band is a feature PR of 200 to 1,500 source lines across 3 to 30 files with a negotiated review thread; 5,000-line PRs are migrations and generated code. The repository-URL source mines that band from python-statemachine, kombu, gql, narwhals, pytest, textual and pypdf.

Non-derivability is the selection rule. Being underspecified is not enough: a strong model solves SymPy's nested Mod simplification from mathematics alone. A task qualifies for the interactive set only if at least one contract-required fact is a choice among reasonable alternatives that neither the code nor domain knowledge determines. Pool B's "tests assume an unstated choice" is often exactly that. And the screen is empirical: a task the frontier tier passes in the hidden condition on every attempt leaves the interactive set, because its underspecification was not load-bearing.

Temporal, thin

One pipeline workflow with a human-approval signal, one trial workflow whose id is the trial id so a retry cannot launch twice, persistent dev server and a systemd worker on a small VM. Its UI is the pipeline-progress screen.

Discovery paths are the honesty mechanism. repo-derivable facts cost nothing to an agent that reads carefully. on-request facts are absent from the repository and required by a test, so asking is necessary rather than rewarded. author-only facts may never be required and never enter any prompt, including the full brief. Every fact carries a source excerpt and URL, or an explicit authored rationale.

Runtime topology

One topology. The hidden material never enters the agent's sandbox. The agent's egress allowlist holds only its model API and the stakeholder host, and that allowlist is the environment baseline, so it also governs the collection phase. Grading happens in a container the agent never enters, on a tarball of its working tree, with no program of the agent's executed during collection.

agentstakeholderverifiercontrol plane, holds no secrets the agent can reach
Why not a compose sidecar
Harbor on Modal and Daytona disables network allowlists whenever a compose file is present; Docker Desktop on the dev Mac fails the egress kernel probe. A hosted service keeps the boundary on a single-container provider.
Why grade a tree, not a container
The agent controls its sandbox, including git. Collection is a tar by Harbor under the allowlist baseline; the verifier diffs against its own pristine checkout and applies only policy-allowed regular-file changes. Pattern adopted from DeepSWE v1.1, tightened after review.
Why strip git history
On SWE-bench Pro, Claude Opus 4.6 and 4.7 ran git log --all and copied the gold patch in over 12% of rollouts. Our images check out a real branch at base, drop remotes and non-ancestor refs, expire the reflog, gc, and validate checks the gold commit is unreachable.

Three conditions, one contract

Each scenario compiles to three Harbor tasks sharing the image, the contract, the grader, and the solver time budget. The three-setting design (full, hidden, interactive) is adopted from Ambig-SWE (Vijayvargiya et al., ICLR 2026) and named as such. What differs is the direction of manufacture: their real artifact is the complete issue and the hidden version is an LLM summary; ours is the issue as filed, optionally withheld further by category with every removed span recorded as a ledger fact carrying the reporter's own words. hidden and interactive always share the same brief, so their difference is the stakeholder alone.

Agent sees: the natural issue plus every stakeholder-visible fact, never author-only material. The most complete statement in every scenario. Stakeholder: none. Purpose: baseline with requirements upfront. Not a ceiling.
Agent sees: the brief selected by the run config: withheld when present (reproduction code, tracebacks, literal expected outputs, locations, version pins and "the fix is" proposals removed, each removal a recorded fact), else natural. Stakeholder: none. Purpose: effect of withholding without a recovery channel; also the empirical screen for non-derivability. At least one scenario runs hidden on both profiles so the cost of withholding is measured, not assumed.
Agent sees: the same brief plus the two shell commands and the stakeholder's availability. Stakeholder: live, session-bound, patience budget owned by code. Purpose: the whole interaction treatment, reported with question, review and stakeholder-token counts alongside and conditioned on questions asked.

Grading and what it resists

Reward is binary correctness on the exact expected-test manifest, computed in the separate verifier. Harbor accepts only numeric values in the reward file, so everything else lives in a report. Integrity signals never change the reward; instead, every control designated an incorrect exploit must score zero or the task is rejected.

reward.json · numeric only
{"reward": 1, "f2p_passed": 2, "f2p_expected": 2,
 "p2p_passed": 187, "p2p_expected": 187,
 "integrity_signal_count": 0, "outcome_code": 1,
 "patch_applied": 1}
report.json · everything else

outcome string, integrity signals with paths, per-test expected vs observed, patch sha256, reviewed-diff sha256, dropped paths, receipt presence, timings.

Outcome classes · all counted
✓valid-correct ✕valid-incorrect ✕agent-invalid-submission ✕agent-runtime-failure ⟳collection-failure ⟳simulator-failure ⟳evaluator-failure

The four agent classes stay in the denominator, including tests that crash because of submitted code and solver timeouts. The three infrastructure classes require external evidence, are retried once, and are shown as counts with lineage to the original attempt.

Infrastructure, verified and planned

The pipeline must run with the laptop closed. One small GCE VM runs the Temporal server with a persistent database, the worker under systemd, and the dashboard. Modal runs every sandbox, image build, verifier, and the stakeholder service. The laptop is a thin client. What ships by the presentation, and what we will not claim

Ships, in critical-path order
  1. Separate verifier with path policy, manifest, numeric reward, report, attribution; real controls on one SWE-bench task
  2. Stakeholder service with session protocol, patience, and a limited tool loop; one interactive episode with a real agent
  3. Full SWE-bench path: mine, judge, draft, approve, compile, validate, register, run, score, export
  4. GitHub repository URL path with bounded discovery; one task through the same stages
  5. Temporal, thin, on the VM; worker-restart check
  6. Tracked example task package and one sanitized run in the repo
  7. Minimal dashboard: table plus episode page; Temporal UI; harbor view
  8. README, grading document, architecture and realism document
We do not claim
  • That any model has not seen a task. A strong full-spec baseline measures performance under that spec, not memorization.
  • That the simulator is deterministic, or realistic beyond its transcripts.
  • That DeepSWE, Pro, or rebench importers exist. They are future sources.
  • That pass rates rank models. Two tiers, k = 3, exact counts, a pilot.
  • That in-process report forgery is impossible.
