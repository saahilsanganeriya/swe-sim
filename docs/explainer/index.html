swesim · design explainer · written for a first-year CS student

Teaching AI coding agents to work with messy instructions

We are building a factory for practice problems. Each problem drops an AI coding agent into a real codebase with a real, incomplete bug report, gives it a pretend teammate who knows the missing details, and grades the result with tests the agent never sees. This page explains why, and how every piece works.

1Four words you need first

Everything below builds on these. If you know them already, skip to section 2.

Agent

A large language model (the same kind of thing as a chatbot) put in a loop with a terminal. It can read files, edit them, and run commands. It keeps going until it decides the job is done. Nobody types the next step; the model chooses it.

Tests

Small programs that check whether code behaves correctly. assert add(2, 2) == 4 is a test. If the code is right, tests pass. If a bug is present, some fail. Most real projects have hundreds of them.

Benchmark

A fixed set of problems plus an automatic grader, so different agents can be compared fairly. In coding, the grader is usually "run the tests".

Reward

The number the grader gives, often just 1 (solved) or 0 (not solved). Reinforcement learning trains a model by having it try problems and nudging it toward whatever earned reward. That is why the grader must be very hard to fool: anything it rewards, the model will learn to do more of.

The most used coding benchmark takes real bugs from real open-source projects on GitHub. Here is one problem, start to finish.

Analogy. It is a take-home exam. You get the question, you hand in your answer, the teacher checks it against an answer key you never saw. Fair, automatic, and completely silent: there is nobody to ask if the question is confusing.

3The catch: real bug reports are messy

Here is a real SWE-bench problem from the SymPy math library. Read the report, then read what the maintainer actually wanted.

The report, as written
Mod(Mod(x + 1, 2) + 1, 2) should simplify to Mod(x, 2)

Currently it does not simplify.

One example. No general rule. No hint of where in the code the problem is, or which cases must not be simplified.

What the maintainer actually wanted, from the discussion
  • Nested Mod should collapse only when the two moduli are the same.
  • Not every operation "commutes with mod", so the rule may only apply to additive structure. The reviewer insisted on a type check.
  • Different moduli must be left alone.

All of that is in the GitHub thread. None of it is in the report.

What SWE-bench Verified did about this

In 2024, OpenAI paid engineers to read 1,699 SWE-bench problems and grade each one: is the report clear enough, and are the tests fair? Then they kept the clean ones. That made a fairer exam. It also removed exactly the situation a working engineer faces every day: an unclear ask, and a colleague to clarify it with.

4Our idea in one picture

Keep the messy report as the question. Add a teammate who knows the answers. Grade with the real fix's tests, hidden, in a clean room.

Analogy. Same take-home exam, but now the question is worded the way the original student wrote it on the forum, and a teaching assistant sits in the room. The TA will explain what the question means if you ask a good question. The TA will not do the problem for you, and does not have the answer key.

5Where the stakeholder's answers come from: the real thread

We do not invent the missing details. Every GitHub issue has a discussion under it, and every fix has review comments. Those are where the maintainer said what they meant. Here is the SymPy thread, condensed, and what each message becomes in our system.

Every fact is tagged with where it came from. Issue thread, PR thread, PR review, the human annotator's note, or "we wrote this ourselves". When we have to change something the history got wrong, for example a test that only passes if you use the exact private helper name the original author picked, we record that as an evaluator repair, not as a fact for the stakeholder to reveal. Nothing is quietly invented.

6The fact ledger: what the stakeholder knows, and how the agent can learn it

The ledger is a short list of facts. The important column is the last one: it says how the agent is allowed to discover each fact. This is how we make sure we never punish an agent for being a careful reader.

Things only the original author knew, like private names. We forbid any test from requiring these.

Why this matters for training. If we gave points for asking questions, a model would learn to ask about everything. If we gave points for finding facts, it would learn to game the fact list. So the reward is only "did the hidden tests pass". Asking pays off exactly when a needed fact is absent from the code, which is what real engineers experience too. How much the agent asked, what it was told, and whether it used it are all recorded, for us to study, never to reward.

7Three versions of every problem

Each problem is compiled three ways. Same code, same hidden tests, same grader. Only the instructions and the presence of the stakeholder change. Comparing the three is how we learn something.

Full. The report plus every ledger fact written out. No stakeholder.
Like an exam with complete, well-written instructions. This is the baseline. It is not a ceiling: agents sometimes do better when they can get feedback than when they get everything upfront.
Hidden. The report only. No stakeholder.
Like the exam with half the question missing and nobody to ask. This is what the original contributor faced before they asked in the thread. The gap between full and hidden measures how much the missing information costs.
Interactive. The report, plus two shell commands: ask-user "…" and request-review, with a budget of questions and review rounds.
Like the exam with the TA in the room. The gap between hidden and interactive measures how much asking helps, and the transcript shows whether the agent asked good questions and used the answers.

Reading a failure honestly

When an interactive run fails, we look at the transcript and the ledger and assign one of these labels. "Unresolved" is allowed. We never blame the stakeholder unless the transcript shows a good question that got a bad answer.

What we observe in the transcriptLabel
The agent asked a relevant question and the answer was withheld or wrongsimulator failure
The task was clearly ambiguous and the agent guessed wrong without askingpotential agent failure
The fact was delivered clearly and the code violates it anywayimplementation or retention failure
Correct result, no questions askedsuccess without clarification
The trace does not show the causeunresolved

8One episode, step by step

An interactive run on the SymPy problem. Orange tags are ledger facts the stakeholder noted it disclosed. The only step that changes the reward is the last one.

  1. agentReads the brief, opens sympy/core/mod.py, runs the existing tests.Finds where the rules live (F4) by reading. No question needed.
  2. agentask-user "Should nested Mod always collapse, or only when the moduli are equal?"Question 1 of a budget of 6.
  3. stakeholder"Only with the same modulus. Mod(Mod(A, c) + B, c) is Mod(A + B, c). Different moduli stay."Disclosed F1 F3. Terse, like the real maintainer. Recorded word for word.
  4. agentImplements the collapse for any inner Mod with equal modulus, adds a test of its own, runs request-review.Review round 1 of 2. Its work is saved as a commit.
  5. review roomApplies the agent's changes to a clean copy and runs two small "review fixtures".One fails: a multiplicative term got collapsed too. These fixtures are not the hidden tests, so review cannot be used to peek at the answer key.
  6. stakeholder"Not all operations commute with mod. Your change also rewrites Mod(Mod(x, c)*y, c). Check the type of the inner term."Disclosed F2. This is based on the agent's actual code, not copied from the 2017 review. A correct first attempt would simply have been accepted.
  7. agentRestricts the rule to additive structure, re-runs tests, declares done.Its changes are exported as a patch. The stakeholder saves the transcript.
  8. graderFresh copy of the code, patch applied, its own tests run: 4 of 4 new tests pass, 212 of 212 old tests pass.Reward 1. Also recorded: 1 question, 1 review round, F1 F2 F3 disclosed, F4 found alone.

9Grading, and how we stop cheating

Remember: whatever the grader rewards, training will amplify. So the grader must be impossible to fool from inside the agent's room. The trick is that we never grade the agent's room at all.

Things a clever agent might try, and why they fail

The trickWhy it does not work
Edit the tests so they pass, or delete themThe grading room uses its own copy of the tests. The agent's copy is ignored.
Add a "skip this test" markerSame: our copy has no marker. And the report lists every test by name, so a missing test reads as a failure, not a pass.
Tamper with the test runner so it reports successRunner settings are ours. Agent-added hook files are removed. The report is cross-checked against the exit code.
Look up the real fix in the project's git historyWe erased the future: the repository is checked out at the moment before the fix, with later commits, branches and tags deleted. This exact trick was caught on SWE-bench Pro in over 12% of one model's runs.
Download the fix from GitHubNo internet from the agent's room except its own AI API and the stakeholder. Verified on Modal today: github.com is unreachable.
Ask the stakeholder for the answerIt holds facts about what is wanted, not code or tests, and refuses "author only" facts by rule, not by judgment.
Use review rounds to probe the hidden testsReview runs different, smaller fixtures, and rounds are budgeted.
Break the patch export so nothing gets gradedA missing or broken patch counts as an invalid submission, scored 0 and kept in the statistics. It does not disappear.

One honest limitation. The code under test runs inside the test process, so a truly malicious patch could interfere with the test run itself. Every unit-test-based grader shares this. We reduce it (unprivileged user, cross-checks, re-running failed tests in isolation) and we say so, rather than claiming it away.

10How we know the grader itself works: five test-takers

Before any problem is accepted, we make five kinds of submission to it and check the grader reacts correctly. A problem whose grader fails any of these is not used.

✓the real fix
Must score 1. Proves the tests detect the historical change.
✕doing nothing
Must score 0. Proves the tests actually fail before the fix.
✕plausible wrong answers
Two or three tempting shortcuts, such as collapsing every nested Mod. Must score 0. Proves the tests catch shortcuts, not just the absence of a fix.
✓a different correct answer
Solves it another way. Must score 1. Proves the tests check behavior, not the original author's exact code.
⚠cheating attempts
The tricks from section 9, as actual patches. Must score 0 or be flagged.
All five outcomes are saved
They appear on the problem's page in the dashboard, so a reviewer can see the grader was tested, not just told it was.

Analogy. Before trusting a new grading rubric, a teacher runs a perfect essay, a blank page, a confidently wrong essay, an unusual-but-correct essay, and a plagiarized one through it. If the rubric gets any of them wrong, the rubric is broken, not the students.

11The factory: how problems get made

All of the above is one problem. The product is the machine that makes many. It is a nine-step pipeline, and every step after the third reads one shared file format, so adding a new source of problems means writing one new "front door".

minefind candidate issue + fix pairs, fetch their threads
judgean AI rates: how hard, how unclear, are the tests fair
specan AI drafts the ledger and persona; a human edits and approves
compilebuild the three versions as Harbor tasks
validatethe five test-takers
registeradd to the dataset with a version
runagents attempt it, in the cloud, several times
scorepass rates, outcomes, failure labels
viewdashboard

Three front doors

Starting point

SWE-bench's rejected problems

The 109-problem pool from section 3, with human notes on what is missing. Environments already exist as prebuilt images, so the first tasks come from here.

Main product

Any GitHub repository link

Paste a repo URL. The pipeline finds merged fixes, follows them back to the issues they closed, keeps the pairs with real discussion and real tests, builds the environment at the right moment in history, and produces tasks. Pointing at a specific PR is optional.

Bonus

DeepSWE

A 2026 benchmark of 113 original, hard tasks already in the same task format. Their detailed instructions become the ledger; a one-line summary becomes the brief.

What "mine" does with a repository link

Keeping the factory running: Temporal

These steps take minutes to hours, talk to flaky external services, and one of them waits for a human. We run the pipeline on Temporal, a system for long-running jobs that remembers exactly where each job is, retries failures automatically, and can pause until a person approves the drafted ledger. Its built-in web page shows every problem's progress through the nine steps, which is a large part of our "see everything happen" requirement for free.

13What we measure, and how to read the numbers

pass@k and pass^k

Agents are random: run the same problem three times and you may get pass, pass, fail. Two questions matter. pass@k: did at least one of k tries succeed? Good for "can it be solved". pass^k: did all k tries succeed? Good for "can it be relied on", which is what a teammate cares about. For pass, pass, fail: pass@3 is yes, pass^3 is no. We report both, with k = 3 as a first pilot.

The gradient we want

A good problem set is not one that every model fails. It is one where weaker models mostly fail and stronger ones mostly succeed, so scores mean something. We measure this by running several model tiers and reporting pass rates per condition. A problem that everyone passes on "hidden", or nobody passes on "full", is flagged and revisited. We never call a pass rate "the difficulty"; it is the difficulty for that agent, that model, that harness, that budget.

Outcomes that are never hidden

✓correct ✕incorrect ✕submitted nothing usable ⟳our collection failed ⟳the stakeholder crashed ⟳the grader crashed

The last three are our fault, get retried once, and are shown as counts. The first three are the agent's, and stay in the denominator. This stops a hard attempt from quietly vanishing from the statistics.

What we refuse to claim

  • That a model has never seen a problem. These are public bugs from 2013 to 2023. A high score on "full" measures skill under that spec, not memory. The GitHub-link front door is how we get to fresh, and eventually private, material.
  • That the stakeholder is realistic beyond what its transcripts show.
  • That any part marked "bonus" or "future" works until it does.

Glossary

patch / diff
The list of exact line changes between two versions of code. What the agent hands in.
base commit
The snapshot of the project just before the real fix was made. Every task starts there.
FAIL_TO_PASS / PASS_TO_PASS
Tests that must go from failing to passing, and tests that must keep passing. Together they are "the contract".
container / sandbox
An isolated computer-in-a-box. Each room in section 12 is one.
allowlist
A short list of internet hosts a room may talk to. Everything else is blocked.
ledger
The stakeholder's list of facts, each tagged with what kind it is, where it came from, and how the agent may learn it.
provenance
Where a fact came from: issue thread, PR review, human annotator, or us.
oracle
The real historical fix, used to prove the grader recognizes a correct answer.
Harbor
The open-source task format and runner that Terminal-Bench and DeepSWE use. We build tasks in its format so any of its 40-plus agents can attempt them.
Modal
A cloud that starts isolated containers in seconds. Where our rooms live.
Temporal
A system for running long, multi-step jobs reliably, with retries and a progress web page.
